# Agent架构说明

## 1. 架构总览

本系统采用**LangGraph状态机 + FastAPI混合架构**，将AI推理流程与传统后端服务分离。

### 1.1 架构图

```
┌─────────────────────────────────────────────────────────────┐
│                    React 前端 (SPA)                          │
└─────────────────────────────────────────────────────────────┘
                              │
                              ▼
┌─────────────────────────────────────────────────────────────┐
│                    FastAPI 后端                              │
│  - 文件上传/解析                                            │
│  - 向量索引管理                                             │
│  - 数据存储                                                 │
└─────────────────────────────────────────────────────────────┘
                              │
                              ▼
┌─────────────────────────────────────────────────────────────┐
│                 LangGraph 状态机层                           │
│  ┌──────────┐ ┌──────────┐ ┌──────────┐                    │
│  │ 知识提取 │→│ 图谱整合 │→│ RAG问答  │                    │
│  │ 状态机   │ │ 状态机   │ │ 状态机   │                    │
│  └──────────┘ └──────────┘ └──────────┘                    │
└─────────────────────────────────────────────────────────────┘
                              │
                              ▼
┌─────────────────────────────────────────────────────────────┐
│                    数据层                                    │
│  ┌──────────┐ ┌──────────┐ ┌──────────┐                    │
│  │ SQLite   │ │ FAISS    │ │ 文件系统 │                    │
│  └──────────┘ └──────────┘ └──────────┘                    │
└─────────────────────────────────────────────────────────────┘
```

### 1.2 设计决策

**为什么选择混合架构？**
1. **职责分离**：文件解析、存储等IO密集任务用FastAPI更高效；AI推理用LangGraph更专业
2. **时间约束**：5小时开发时间，混合架构最灵活
3. **易于调试**：传统后端可直接测试，AI部分单独验证

**为什么不用纯LangGraph？**
- 过于复杂，状态机节点多，prompt长
- 文件解析等非AI任务用状态机是浪费
- 难以独立测试单个功能

## 2. LangGraph状态机详解

### 2.1 知识提取状态机

**状态定义：**
- `START` → `parse_chapter` → `extract_concepts` → `extract_relations` → `validate_output` → `store_results` → `END`

**节点说明：**

| 节点 | 输入 | 输出 | 职责 |
|------|------|------|------|
| parse_chapter | 章节文本 | 结构化段落 | 分段、清洗文本 |
| extract_concepts | 段落列表 | 概念列表 | 调用LLM提取概念名称、定义、分类 |
| extract_relations | 概念列表 | 关系列表 | 调用LLM识别概念间关系 |
| validate_output | 概念+关系 | 验证结果 | 检查JSON格式、字段完整性 |
| store_results | 验证通过的数据 | 存储确认 | 写入SQLite数据库 |

**条件边逻辑：**
- validate_output 失败 → 回到 extract_concepts 重试（最多3次）
- validate_output 成功 → 进入 store_results

### 2.2 图谱整合状态机

**状态定义：**
- `START` → `load_knowledge_graph` → `compute_similarity` → `llm_judge` → `apply_decisions` → `verify_compression` → `END`

**节点说明：**

| 节点 | 输入 | 输出 | 职责 |
|------|------|------|------|
| load_knowledge_graph | 数据库 | 全部节点和边 | 加载完整知识图谱 |
| compute_similarity | 节点列表 | 相似度矩阵 | 使用FAISS计算向量余弦相似度 |
| llm_judge | 相似节点对 | 合并/保留/删除决策 | 对0.7-0.85区间的节点调用LLM判断 |
| apply_decisions | 决策列表 | 更新后的图谱 | 执行合并、删除操作 |
| verify_compression | 更新后图谱 | 压缩比 | 验证压缩比 <= 30% |

**条件边逻辑：**
- verify_compression 压缩比 > 30% → 回到 llm_judge 调整决策
- verify_compression 压缩比 <= 30% → 结束

### 2.3 RAG问答状态机

**状态定义：**
- `START` → `embed_query` → `retrieve_context` → `build_prompt` → `generate_answer` → `add_citations` → `END`

**节点说明：**

| 节点 | 输入 | 输出 | 职责 |
|------|------|------|------|
| embed_query | 用户问题 | 查询向量 | 使用Embedding模型生成向量 |
| retrieve_context | 查询向量 | 相关文档块 | FAISS检索Top-K相关块 |
| build_prompt | 问题+上下文 | 完整Prompt | 注入系统指令和检索结果 |
| generate_answer | Prompt | LLM回答 | 调用LLM生成回答 |
| add_citations | 原始回答 | 带引用回答 | 添加来源引用标记 |

## 3. 数据流详解

### 3.1 教材处理流程
```
用户上传 → FastAPI接收 → 文件解析器 → SQLite存储 → 返回成功
```

### 3.2 知识提取流程
```
触发提取 → 读取章节 → LangGraph状态机 → LLM提取 → 存储节点/边
```

### 3.3 RAG问答流程
```
用户提问 → 向量嵌入 → FAISS检索 → 构建Prompt → LLM生成 → 返回答案
```

### 3.4 完整数据流图

```
教材PDF/MD/TXT
      │
      ▼
  文件解析器 (FastAPI)
      │
      ├─→ SQLite (原始文本、章节结构)
      │
      ▼
  知识提取 (LangGraph)
      │
      ├─→ SQLite (知识点节点、关系边)
      │
      ▼
  向量化 (FAISS)
      │
      ├─→ FAISS索引文件
      │
      ▼
  图谱整合 (LangGraph)
      │
      ├─→ SQLite (更新后的节点、边)
      │
      ▼
  RAG问答 (LangGraph)
      │
      └─→ 带引用的答案
```

## 4. Prompt工程

### 4.1 知识提取Prompt

**系统指令：**
```
你是一个医学知识提取专家。请从以下文本中提取知识概念和它们之间的关系。

要求：
1. 每个概念包含：name（名称）、definition（定义）、category（分类）
2. 关系类型：prerequisite（前置依赖）、parallel（并列）、contains（包含）、applies_to（应用）
3. 输出严格的JSON格式
4. 只提取明确陈述的知识点，不要推断
```

**Few-shot示例：**
```json
{
  "concepts": [
    {
      "name": "炎症",
      "definition": "具有血管系统的活体组织对损伤因子所发生的防御反应",
      "category": "病理学"
    }
  ],
  "relations": [
    {
      "source": "炎症",
      "target": "血管反应",
      "type": "contains"
    }
  ]
}
```

**设计要点：**
- 明确要求JSON格式输出，便于程序解析
- 给出few-shot示例，减少LLM输出格式错误
- 限制每次只处理一个章节，避免上下文过长

### 4.2 RAG问答Prompt

**系统指令：**
```
你是一个医学知识问答助手。请基于以下知识库内容回答用户问题。

规则：
1. 只基于提供的上下文回答，不要使用外部知识
2. 如果上下文中没有相关信息，请回复"当前知识库中未找到相关信息"
3. 在回答末尾附带来源引用，格式：[教材名, 章节, 页码]
4. 回答要准确、简洁、专业
```

**上下文注入模板：**
```
以下是从知识库中检索到的相关内容：

---
来源：{textbook_name}, 第{chapter}章, 第{page}页
内容：{content}
---

用户问题：{question}
```

**设计要点：**
- 约束只基于上下文回答，避免幻觉
- 要求附带来源引用，增强可信度
- 无法找到时明确回复，不胡编乱造

## 5. 错误处理与重试策略

### 5.1 LLM调用失败
- 重试次数：最多3次
- 退避策略：指数退避（1s, 2s, 4s）
- 降级方案：返回部分结果，标记失败章节

### 5.2 JSON解析失败
- 重试次数：最多2次
- 策略：调整Prompt增加格式约束
- 降级方案：记录原始输出，人工审核

### 5.3 向量检索为空
- 策略：降低相似度阈值重试
- 降级方案：返回"未找到相关内容"

## 6. 取舍与权衡

### 6.1 已知局限
- 单机部署，不适合大规模并发
- 依赖外部LLM API，离线不可用
- SQLite不适合高并发写入

### 6.2 放弃的方案
- 纯LangGraph架构：过于复杂，所有逻辑都用状态机，开发效率低
- 微服务架构：部署复杂，5小时时间不够
- 本地LLM：资源消耗大，推理速度慢

### 6.3 未来改进方向
- 分布式部署：Redis + Celery异步任务队列
- 缓存优化：缓存常见问题的回答，减少LLM调用
- 本地模型：Ollama支持，降低API成本
- 增量更新：支持教材内容变更后的增量索引
